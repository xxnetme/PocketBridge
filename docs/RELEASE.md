# Выпуск и обновление PocketBridge

Начиная с **v4.0.1** (`versionCode 26`) официальный APK для установки напрямую называется `PocketBridge-v<версия>.apk` (без `-debug`). Идентификатор остаётся `com.local.wififiles`. Для обновления поверх Android должен видеть то же приложение, тот же сертификат подписи и не меньший `versionCode`; PocketBridge для следующего выпуска требует **строго больший** `versionCode`. Сертификат APK — не локальный HTTPS-сертификат телефона.

<a id="migrate"></a>
## Для тех, у кого уже установлен PocketBridge

- **Если установлен официальный APK с тем же сертификатом:** откройте новый APK и выберите «Обновить». **Не удаляйте** старую версию. Настройки приложения остаются на месте. Активный сервер или передача может остановиться при обновлении; завершите передачу заранее.
- **Если установлен `-debug.apk` v3.9 или v4.0:** опубликованные сборки этих двух версий подписаны разными сертификатами. При переходе на новый постоянный ключ Android не разрешит установку поверх. Перед одноразовым удалением запишите язык, порт, общую папку, режим доступа и другие нужные настройки; скопируйте важные файлы, в том числе из `PocketBridge Inbox`. Автоматического переноса настроек при удалении нет. После установки стабильного APK разрешите доступ к файлам и настройте приложение заново. Не удаляйте приложение, пока не убедитесь, что копии данных доступны.
- Если установщик сообщает о конфликте пакетов, сначала проверьте, что APK скачан из нужного релиза и подходит к установленной сборке. Не обходите проверку подписи. Сборки из Actions с меткой `debug` предназначены для разработки, а не обновления стабильной версии.

Для проверки скачанного APK распаковывать его не нужно. Скачайте `SHA256SUMS.txt`, APK, AAB и `APK-SIGNER-SHA256.txt` из того же релиза в один каталог и выполните:

```bash
sha256sum --check SHA256SUMS.txt
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --print-certs PocketBridge-v4.0.1.apk
```

Сверьте `Signer #1 certificate SHA-256 digest` с **отпечатком из доверенного источника**: опубликованным владельцем проекта или проверенным предыдущим официальным APK. Контрольная сумма файла сама по себе не подтверждает, кто его выпустил. AAB — формат публикации в магазине, а не APK для непосредственной установки. Подпись APK из Google Play может отличаться при Play App Signing.

## Для владельца: один ключ на все выпуски

Кандидат **4.9.0** имеет `versionCode 29`. Сценарий стабильного выпуска 4.9.0 требует опубликованного первого стабильного **v4.0.1** и APK предыдущего стабильного релиза с проверенной подписью владельца. Если v4.0.1 ещё не опубликован, сначала пройдите его проверки и выпустите его с постоянным ключом. Ни опубликованные старые debug-APK, ни APK, подписанные временным ключом для теста обновления, не заменяют этот исходный релиз. Запустите `Build & Test` вручную на коммите-кандидате, чтобы проверить обновление на API 29 и 36 **до** создания релизного тега.

1. Если постоянный ключ уже есть, используйте его. Иначе создайте ключ **на своём компьютере**, а не на CI. Например, с JDK 21 и Bash:

   ```bash
   install -d -m 700 "$HOME/pocketbridge-keys"
   KEYSTORE="$HOME/pocketbridge-keys/pocketbridge.p12"
   (umask 077; keytool -genkeypair -storetype PKCS12 -keystore "$KEYSTORE" \
     -alias pocketbridge -keyalg RSA -keysize 3072 -validity 10950 -dname 'CN=PocketBridge')
   keytool -list -v -keystore "$KEYSTORE" -alias pocketbridge
   ```

   `keytool` спросит пароль. Возьмите **SHA256 отпечаток сертификата** из вывода последней команды, не хеш файла `.p12`. Храните не меньше двух защищённых резервных копий ключа вне репозитория и CI. Пароли храните отдельно от копий, например в менеджере паролей; проверьте, что копия открывается и отпечаток совпадает. Потеря закрытого ключа лишит возможности обычного APK-обновления. Не передавайте хранилище, base64, пароли или токены в чат, в коммит или в логи.
2. В GitHub: **Settings → Environments → `release`**. В **Deployment branches and tags** выберите **Selected branches and tags** и добавьте только правила типа **Tag**, например `v*`, без правила для веток. Ограничьте создание тегов `v*` доверенными сопровождающими и запретите их перемещение/удаление (rulesets, где доступны); защитите `main`. Если тариф поддерживает подтверждение деплоя для приватного репозитория, включите его для доверенного проверяющего. Один лишь `environment: release` в YAML не заменяет эту настройку на GitHub.
3. Добавьте в окружение `release`, **не на уровень репозитория**:

   | Тип | Имя | Значение |
   | --- | --- | --- |
   | Environment variable | `PB_SIGNER_SHA256` | Независимо проверенный SHA-256 отпечаток сертификата: 64 hex-символа, можно с двоеточиями между байтами. Не секрет. |
   | Environment secret | `PB_KEYSTORE_BASE64` | Base64 всего файла хранилища. |
   | Environment secret | `PB_KEYSTORE_PASSWORD` | Пароль хранилища. |
   | Environment secrets, опционально | `PB_KEY_ALIAS`, `PB_KEY_PASSWORD` | Если отличаются от `pocketbridge` и пароля хранилища соответственно. |

   Если используете авторизованный `gh`, передайте Base64 напрямую, не создавая промежуточный файл:

   ```bash
   base64 < "$KEYSTORE" | tr -d '\r\n' | gh secret set PB_KEYSTORE_BASE64 --env release
   ```

   Base64 — только способ передать двоичный файл, не шифрование. Если прежние секреты с этими именами заведены на уровне репозитория или организации, уберите их оттуда для этого проекта. Для приватного репозитория окружения и секреты окружения требуют подходящего GitHub-плана ([документация](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)). Если их нет, храните ключ локально, **не** переходите на секреты репозитория. Собирайте и проверяйте вручную по инструкции ниже после прохождения CI без ключа.
4. После проверок [на Android](DEVICE-CHECKS.md) и прохождения CI на `main` поставьте аннотированный тег **на проверенный коммит**. Для первого выпуска:

   ```bash
   git switch main
   git pull --ff-only
   git tag -a v4.0.1 -m 'PocketBridge v4.0.1 — Обновление без переустановки'
   git push origin v4.0.1
   ```

   В Actions проверьте задания `Verify Android upgrade without reinstall`, `Build and verify the permanently signed APK` и `Publish the verified GitHub Release`. Обычные PR и ветки не получают ключ и не публикуют GitHub Release. Тег без секретов, без отпечатка, с чужим сертификатом или с пропавшим предыдущим стабильным APK не превращается в релиз из debug-сборки. Начиная со второго стабильного релиза CI скачивает последний опубликованный стабильный APK, проверяет его подпись и требует тот же сертификат и больший `versionCode`. Храните оригинальные файлы релизов и их контрольные суммы; не удаляйте их при выходе обновлений.

### Проверенный локальный release (Linux)

Нужны JDK 21, Python 3.11+, Android SDK (`ANDROID_HOME`, SDK Platform 36, Build Tools 36.0.0) и `curl`. Работайте из чистого checkout проверенного коммита. Сначала сохраните результаты CI и тестов на телефонах. Для выпусков после v4.0.1 скачайте предыдущий APK из официального стабильного релиза (не из Actions) и укажите его третьим аргументом. Если нужно отдать файл владельцу для публикации, передавайте **только проверенные артефакты**, не хранилище.

```bash
export PB_KEYSTORE="$HOME/pocketbridge-keys/pocketbridge.p12"
read -rsp 'Пароль хранилища: ' PB_KEYSTORE_PASSWORD; echo
export PB_KEYSTORE_PASSWORD
read -rp 'SHA-256 отпечаток сертификата: ' PB_SIGNER_SHA256
export PB_SIGNER_SHA256
# После v4.0.1 укажите новый тег и добавьте путь к предыдущему стабильному APK.
tools/sign-release.sh v4.0.1 ./release-v4.0.1
unset PB_KEYSTORE_PASSWORD PB_KEYSTORE PB_SIGNER_SHA256
```

Папка результата не должна существовать заранее. Скрипт проверит пакет, версии, подпись APK и AAB, выравнивание APK и, если указан предыдущий стабильный APK, совместимость обновления. Он сохранит `PocketBridge-v4.0.1.apk`, `.aab`, `APK-SIGNER-SHA256.txt` и `SHA256SUMS.txt`. Проверенный экземпляр bundletool 1.18.3 можно предоставить через `PB_BUNDLETOOL_JAR`; иначе скрипт скачает его и сверит закреплённый SHA-256. Если используются нестандартные alias или пароль ключа, передайте `PB_KEY_ALIAS`/`PB_KEY_PASSWORD` через окружение и также очистите их после сборки. Если сборка проводится вне GitHub, публикуйте через интерфейс Releases только эти четыре файла под проверенным тегом, не перезаписывая существующий релиз.
